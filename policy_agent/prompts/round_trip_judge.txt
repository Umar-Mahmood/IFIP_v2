You are checking whether two descriptions of a Kubernetes NetworkPolicy
request specify the EXACT SAME policy. You will be given:
  A: the original request, in whatever words the user chose
  B: a reconstructed sentence built from fields an extractor parsed out of A

Wording, tone, sentence structure, and order do NOT matter — ignore them
completely. Only compare the concrete, load-bearing details:
  - direction: is this about egress (pods reaching OUT to a CIDR) or
    ingress (things reaching IN to pods)?
  - the CIDR value itself, compared character-for-character (100.0.32.0/24
    is NOT the same as 100.0.16.0/24 — a single differing octet is a
    DIFFERENT policy, even though the sentences otherwise look identical)
  - allow vs deny / block direction — is the named CIDR the one being
    PERMITTED or the one being BLOCKED? A sentence that swaps this word
    describes the OPPOSITE policy even if every other word matches.
  - port/protocol, if either sentence specifies one
  - peer NAMESPACE identity (for rules about "namespace X" as a peer, not a
    CIDR) — compared exactly like a CIDR would be; a different namespace
    name is a different policy
  - when MULTIPLE ports/protocols are listed, every one of them must match —
    a missing or extra port/protocol in either sentence is a different policy
  - when MULTIPLE labels are listed for selecting pods (target pods or peer
    pods), every label (key AND value) must match — a subset, a superset, or
    a different label set is a different policy
  - a sentence describing BOTH an ingress rule AND an egress rule together
    needs BOTH sides to match independently — if either side differs, they
    are different policies even if the other side is identical

IMPORTANT — "ipBlock cidr: 0.0.0.0/0 and except: [X]" phrasing: this is a
common way to express "block X, allow everything else." Read it carefully:
0.0.0.0/0 means ALL addresses; "except: [X]" REMOVES X from that allowed
set. So the net effect is X is BLOCKED and everything else is ALLOWED —
this is a BLOCK/DENY of X, not an allow of X. Do not be fooled by the word
"allow" appearing next to "0.0.0.0/0" into thinking X itself is allowed.

This is a rule for correctly READING B when B happens to use that phrasing
— it is NOT a shortcut for skipping the comparison. Seeing the except-clause
in B does not by itself make same_meaning true. You must still separately
work out what A actually says (does A allow only X, or block X?) and check
it matches what B means (block X, allow rest). If A says "only allow X,
deny everything else" — that is the OPPOSITE of what the except-clause
phrasing means, even though X appears in both sentences.

Return ONLY a JSON object, no prose, no markdown fences:
{"same_meaning": <bool>, "reason": "<one short sentence citing the specific
detail that matched or differed>"}

{"same_meaning": true, "reason": "same CIDR 100.0.18.0/24, same allow direction, same port 80"}
